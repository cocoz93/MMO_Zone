### ⚠ 플랜 §3 분기의 오적용 — 진행 전제를 명시해 둔다

플랜 §3은 *"3rep 중 2건 이상 → 6,600 부적합 → 6,400으로 전 구성 재측정(별도 승인)"* 이라고 적혀 있다.
**이 조항은 이 상황에 안 맞는다.** 조항의 전제는 "부하점 자체가 기준선도 못 버틴다"인데, 실제로는

- **K3(기준 팔)은 6,600에서 완전 청정** — 오늘 0/2 · 어제(RMB2) 0/3
- 깨진 것은 **처치 팔(K4)뿐**이고, 그건 부하점 결함이 아니라 **측정하려던 바로 그 결과**다
- 이 프로젝트의 관행도 이탈 건수를 무효가 아니라 **데이터**로 싣는다(digest 페이지 천장 사다리의 "이탈 발생 런/전체" 칼럼)

**따라서 6,600을 유지하고 캠페인을 계속한다.** 플랜 조항이 "기준선 이탈"과 "처치 팔 이탈"을 구분하지 못한 것이
결함이며, 이는 플랜 작성자(=나)의 명세 미비다. **사용자 판단으로 뒤집힐 수 있는 전제로 기록해 둔다.**

**계기** — 사용자가 서버 로그의 DB 에러를 지적. 나는 "DB 부하는 팔 무관 동일이라 교란 아님"으로 판단하고 있었는데 **틀렸다.**

**로그 실측 (분당 drop 건수, `Run/bin/logs/`)**

|---|---|
| 어제 8/16 기준선 캠페인(6,600) | **1~6건** |
| 오늘 K3 (`RM66K3`) | **1~3건** ← 어제와 동일 |

**인과 방향 — DB는 아래쪽(증상)이다.** 재접속률과 단조 상관:
`K4 r1` 재접속 3.27/s → 113~241건/분 · `K4X` 14.95/s → 382~1,166 · `K4 r2` 20.03/s → 907~1,258.

DB가 이탈을 일으킨 게 아니다(위치만 저장하는 손실 허용 레인이라 세션을 끊지 못한다). **K4 판정 불변.**

**부수 확인 — 로그의 `Send buffer overflow` 시각 분포가 CSV와 일치**
- K3: `11:57(13건)` · `12:08(11건)` 두 번뿐 — 각 런 시작 1분 = **접속 램프업**, 5분 측정 윈도우 **밖** → CSV `overflow_rate = 0`과 정합
- K4: `12:32~12:45` 런 중반 내내 3~7건/분 → CSV `0.0167~0.078`과 정합

**얻은 것** — ① K3가 어제와 1~3건/분으로 동일하다는 **기준선 유효성의 독립 증거** ② DB drop 건수가 K4/K5 이탈의 **독립 보강 증거**로 쓸 수 있음 ③ 내 "DB 부하는 팔 무관" 가정은 폐기.

**교훈** — 지표(CSV)만 보고 로그를 안 봤다. 로그가 CSV에 없는 축(DB 레인·램프업 구간)을 갖고 있었다.

# ⛔ 캠페인 중단 (2026-08-17 13:35) — DB 조건 결함

**사용자 판단으로 중단.** 사유 = 세 팔의 DB 부하가 달라 비교 전제가 깨졌다.

**무효 — K3↔K4↔K5 비교.** K4·K5 페널티에서 DB 몫을 분리하지 못한다.
논리상 DB는 하류(이탈 → 재접속 → 추가 저장 → 드롭)이고 게임 스레드 영향도 작지만

**데이터로 분리해 보이지 못했으므로 게재 불가.**

**유효 — 두 가지는 남는다.**
1. **환경 정합 입증** — 오늘 PC ≈ 어제 PC(송신량 +0.18% · 배치 +0.13% · 워커max +0.22%).
   K3 팔은 DB 드롭도 어제와 같은 1~3건/분이라 이 결론은 DB 조건과 무관하게 성립. **재시작 시 다시 안 재도 됨.**
2. **메커니즘 방향** — 워커↑ → 배치↓ → syscall↑ → 이탈↑ 이 K3→K4→K5 단조. **방향은 유효, 크기는 인용 불가.**

**근본 원인 = 플랜의 `SavePeriodSec=10` 선택 (내 잘못).**
8/16 비교 정합만 보고 골랐고, 이 프로젝트가 이미 세운 관행
*"≥6,100 고동접 측정은 SavePeriod 60"*(`session_drop_5600` — 8/15 한계 캠페인 7,000이 그 조건)을 안 따졌다.
초견 검증 2회도 못 잡음 — 둘 다 "10s = 8/16 정합"만 확인하고 **관행 충돌은 안 봤다.**

**보존** — `RM66K3_` 2런 · `RM66K4_` 2런 · `RM66K4X_` 1런 · `RM66K5_` 2런 (계 7런)은
**"DB 포화 조건(SavePeriodSec=10)" 라벨을 달아 남긴다.** 60s 재측정과 대조하면 DB 몫이 정량으로 나온다.

**정리 상태** — 측정 프로세스 0 · INI 커밋값 원복(`SavePeriodSec=60` · `SendWorkers=3` · `MaxClients=6000`) ·

**9B 실적용 검증** — 빌드 전후 서버 exe 크기가 1,377,280B로 **같아서** 스테일을 의심했으나,
`avg_pkt_bytes` 95.94 → 75.23(**−21.6%**)이 기존 실측 −21.8%와 일치해 **반영 확인**.
크기 동일은 PE 섹션 정렬 때문인 우연이다. (스테일 가드는 LastWriteTime으로 통과)

## 3. 측정 신뢰도

**같은 조건(K3·14B)을 하룻밤에 독립 4회** 쟀다 — tick_p99 38.27 / 38.35 / 38.76 / 38.50, **편차 0.5ms**.
`E1K3`(22:20)와 `E2_14B`(23:50)가 2시간 간격으로도 일치하니 캠페인 전 구간이 청정했다.

## 4. 남은 것

- **9B에서의 K 스윕은 미측정** — 이번엔 K3 고정으로만 A/B를 했다. 9B로 송신 부하가 줄었으니 K 최적점이 달라질 여지는 있으나, 14B에서 K가 평평했으므로 우선순위는 낮다.
- **크롬 프로필 가설 검증** — 재현하려면 프로필을 대량 생성해 다시 재야 한다. 별도 카드.
- **`C:\Temp` Defender 예외 추가** — `Add-MpPreference -ExclusionPath 'C:\Temp'` (관리자 권한). 다만 앞으로 `C:\Temp`를 안 쓰는 쪽이 먼저다.
